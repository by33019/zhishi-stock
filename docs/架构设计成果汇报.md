## 1. 汇报摘要

本次架构设计优先复核并采用了项目 PDF 的核心工程思路。PDF 已将系统分为股票终端展示、股票数据采集、缓存与数据库，并使用 `stock_parent` 聚合 `stock_common`、`stock_backend` 和 `stock_job`。该方向适合当前项目，不需要推翻重做。

最终架构为：

**模块化单体代码库 + `stock-api` 在线服务 + `stock-job` 数据任务进程 + `stock-ai-worker` AI 任务进程 + MySQL + Redis + XXL-JOB + Nginx/Vue3 + Docker Compose。**

该方案在保留 PDF 架构主线的同时，补齐了 PRD 所需的新闻、AI、自选、实时推送、安全、可观测性和容器化部署能力。

## 2. 输入资料与分析结论

### 2.1 PDF 资料

PDF 给出的主要技术和工程设计包括：

- 前端：Vue、Element、Axios、ECharts、Nginx。
- 后端：Spring Boot、MyBatis、Spring MVC、Spring Security、JWT。
- 缓存：Redis、Spring Cache。
- 定时任务：XXL-JOB。
- 导出：EasyExcel。
- 数据扩展：Sharding-JDBC。
- Maven 模块：`stock_parent`、`stock_common`、`stock_backend`、`stock_job`。

其中 Maven 多模块、独立 Job、Redis、JWT、XXL-JOB、ECharts 和 Nginx 被采用；Vue/MyBatis 分别升级为 Vue3/MyBatis-Plus；Sharding-JDBC 暂不进入 MVP。

### 2.2 PRD 资料

PRD 要求平台提供市场、板块、榜单、个股、资讯、自选、AI 研究、历史和后台管理，并满足以下关键指标：

- 交易时段核心行情延迟不超过 60 秒。
- AI 首段 P95 不超过 5 秒，完整结果 P95 不超过 30 秒。
- 支持 500 个并发浏览会话和 30 个并发 AI 任务。
- AI 结果必须包含证据、数据截止时间、风险和非投资建议声明。
- 外部行情、新闻或大模型异常时，基础行情仍可降级运行。

### 2.3 SQL 资料

现有 SQL 有 11 张表，可支撑国内外指数、板块、个股实时快照、主营业务、用户、角色、权限和操作日志。

架构设计识别出的主要缺口包括：

- 缺少证券主数据、交易日历和涨跌停规则。
- 缺少分钟 K 线、日 K 线和复权基础数据。
- 缺少新闻、公告和股票/板块关联。
- 缺少自选股。
- 缺少 AI 任务、会话、报告、证据、反馈和用量数据。
- `block_label` 长度和 `sys_log.user_id` 类型存在不一致。
- 关系表缺少防重复联合索引，邮箱注释唯一但没有唯一索引。

## 3. 整体架构成果

### 3.1 三个运行进程

| 运行进程 | 核心职责 | 隔离价值 |
| --- | --- | --- |
| `stock-api` | REST、JWT/RBAC、WebSocket、SSE、在线查询、自选和历史 | 保证用户请求不被采集与 AI 长任务占用 |
| `stock-job` | 行情/指数/板块/新闻采集、K 线聚合、榜单、预热和清理 | 外部数据源失败不会拖垮在线服务 |
| `stock-ai-worker` | AI 任务、上下文、LLM 调用、流式片段、证据和结果校验 | 模型超时、限流和高内存使用与 API 隔离 |

### 3.2 Spring Boot 模块

后端规划为 `stock-common`、`stock-system`、`stock-market`、`stock-news`、`stock-watchlist`、`stock-ai`、`stock-integration`、`stock-backend`、`stock-job` 和 `stock-ai-worker`。

业务模块拥有自己的领域对象、用例和 Mapper，禁止 Controller 直接调用 Mapper，也禁止跨模块读取其他模块的数据库实体。`stock-common` 只保留真正稳定的通用能力，避免演变成无边界的公共代码仓库。

### 3.3 实时行情链路

1. XXL-JOB 按交易时段触发 `stock-job`。
2. `stock-job` 分批调用第三方行情 API。
3. 数据标准化和质量校验后，最新快照写入 Redis。
4. 同一分钟报价聚合后批量写入 MySQL。
5. Redis Pub/Sub 发布行情变化。
6. `stock-api` 将变化通过 WebSocket 推送给已订阅页面。
7. 浏览器断线重连后通过 REST 获取完整快照，不依赖 Pub/Sub 补发。

### 3.4 AI 链路

1. `stock-api` 校验 JWT、权限、参数、配额和并发。
2. MySQL 创建 AI 任务，Redis Stream 投递任务。
3. `stock-ai-worker` 固化行情和资讯证据，调用大模型 API。
4. 流式片段经 Redis 中继，由 `stock-api` 通过 SSE 返回浏览器。
5. Worker 完成结构、引用和安全校验后，将报告、证据和用量写入 MySQL。
6. 任务失败可恢复，Redis 丢失后可根据 MySQL 待处理任务重新入队。

## 4. 数据存储成果

### 4.1 MySQL

MySQL 保存最终业务事实：

- 用户、角色、权限和审计日志。
- 证券主数据、交易日历和规则版本。
- 个股、指数、板块分钟数据和日 K 数据。
- 新闻、公告、来源、去重和标的关联。
- 自选分组和自选股票。
- AI 任务、会话、消息、报告、证据、反馈和用量。
- 任务执行摘要和数据质量结果。

### 4.2 Redis

Redis 保存可过期或可重建的高频状态：

- 个股、指数和板块最新行情。
- 涨跌榜、成交额榜和市场广度。
- 热门 K 线和最新资讯缓存。
- JWT 刷新会话、撤销 Token、验证码、登录失败计数和权限缓存。
- AI 配额、并发占位、任务状态、Redis Stream 和流式文本片段。
- WebSocket 行情 Pub/Sub、定时任务锁和幂等键。

Redis 不作为账户、自选、新闻或 AI 报告的唯一存储。

### 4.3 实时查询

- 个股/指数/板块最新行情、市场广度和榜单优先查询 Redis。
- 分时和热门 K 线使用 Redis 热缓存，回退 MySQL。
- 历史 K 线、历史资讯、自选、权限和 AI 历史查询 MySQL。
- 用户在线请求不直接访问第三方行情和新闻 API。

## 5. WebSocket 和 AI 位置结论

### 5.1 WebSocket

WebSocket 有必要使用，但只承担实时行情增量推送。首屏使用 REST，实时变化使用 WebSocket，断线后再用 REST 重建。AI 文本生成继续采用 SSE，因为它是单向流式输出；普通业务操作继续使用 REST。

登录用户通过短期、单次使用的 WebSocket Ticket 建立私有连接，避免把长期 JWT 放在 URL。每个连接最多订阅 50 个动态主题，并通过序列号识别丢包。

### 5.2 AI 模块

AI 代码位于 `stock-ai`，执行位置为独立 `stock-ai-worker`。MVP 不单独引入 Python + FastAPI；`stock-ai-worker` 使用稳定任务契约和 Provider Port，V1.2 可以替换为消费同一 Redis Stream 的 FastAPI Worker，前端和 API 协议不变。

## 6. 定时任务成果

核心任务包括：

- 每日同步交易日历、证券主数据和规则。
- 开盘前预热行情、搜索和热点缓存。
- 交易时段每 15-30 秒采集 A 股和指数，每 30-60 秒采集/聚合板块。
- 每 2 分钟增量采集新闻和公告。
- 行情批次后实时计算市场广度和榜单。
- 收盘后聚合并校验日/周/月 K 线。
- 定期恢复卡死 AI 任务、检查缓存一致性、清理过期数据和汇总指标。

核心业务任务由 XXL-JOB 管理，保留日志、分片、重试、告警和人工重跑能力。

## 7. Docker Compose 部署成果

默认 Compose 服务包括：

- `nginx`
- `stock-api`
- `stock-job`
- `stock-ai-worker`
- `mysql`
- `redis`
- `xxl-job-admin`

可选 `observability` Profile 包含 Prometheus、Grafana、Loki 和 Promtail；可选 `backup` Profile 负责 MySQL 备份。

生产环境只暴露 Nginx 的 80/443，数据库、Redis、XXL-JOB 和应用端口仅在内部 Docker 网络开放。MySQL、Redis、证书、日志和备份使用独立 Volume，生产密钥使用 Compose Secrets 或外部密钥管理。

## 8. 关键取舍

| 取舍 | 结论 | 原因 |
| --- | --- | --- |
| 单体还是微服务 | 模块化单体 | 当前容量和团队规模不需要微服务治理成本 |
| 是否保留 PDF Job 模块 | 保留并强化 | 采集、聚合和清理必须与在线 API 隔离 |
| 是否使用 Sharding-JDBC | MVP 不使用 | 优先通过批量写入、索引、时间分区和保留策略解决 |
| 是否增加消息队列 | 不增加独立 MQ | Redis Streams 足以支撑当前 AI 并发与恢复 |
| 是否使用 WebSocket | 使用 | 仅处理行情增量推送，减少页面轮询 |
| AI 是否放在 API 进程 | 不放 | 长任务和第三方故障需要独立资源与恢复能力 |
| 是否首版使用 FastAPI | 不使用 | 降低首版技术栈和运维复杂度，保留替换契约 |
| 是否直接查询第三方 API | 用户请求不直查 | 避免供应商故障、限流和耗时传导给用户 |

## 9. 主要风险

1. 单机 Compose 的 MySQL、Redis和宿主机仍是单点，需要离机备份和恢复演练。
2. 全市场分钟数据增长较快，需要时间分区、批量写入、90 天分钟数据保留和容量告警。
3. 第三方 API 的调用额度决定实际采集频率，签约前需要验证批量接口和限流规则。
4. Redis Pub/Sub 不提供离线重放，因此 WebSocket 必须使用 REST 快照恢复。
5. AI 引用和安全校验不能依赖模型自觉，必须由应用代码和证据白名单强制执行。
6. 现有 SQL 不能直接满足 PRD，需要单独完成数据库详细设计和 Flyway 迁移方案。
