## 产品摘要

AI 智能股票分析平台是在现有“今日指数”行情分析系统基础上的产品化升级。平台保留大盘、板块、榜单、个股行情、K 线、主营业务、权限和日志等基础能力，新增资讯、自选股和场景化 AI 研究能力。产品不是将聊天框简单叠加到行情页面，而是把 AI 嵌入市场、板块、个股和自选股场景，在用户查看数据时提供可追溯、可追问、明确标注时效与不确定性的辅助分析。

产品核心价值闭环为：

`发现市场变化 -> 查看行情证据 -> 获取 AI 解读 -> 核验资讯来源 -> 加入自选持续跟踪 -> 沉淀分析历史`

### 产品原则

1. 事实优先：所有 AI 结论必须基于平台提供的行情或授权资讯，不得虚构来源。
2. 证据可查：分析结论附带数据截止时间、证据编号和可点击来源。
3. 风险对称：同时呈现支持因素、反例、风险与不确定性，不只强化单一方向。
4. 决策归用户：不输出确定性买卖指令、具体仓位、保证性目标价或收益承诺。
5. 降级可用：上游行情、资讯或 AI 服务异常时，基础行情能力仍可使用，并明确标记数据状态。
6. 权限隔离：游客、注册用户和管理员仅能访问各自被授权的数据和操作。

# 1. 项目背景

## 1.1 市场背景

A 股个人投资者通常需要在行情软件、新闻网站、公司公告和社区观点之间频繁切换。传统行情平台擅长提供价格、涨跌幅、成交量等数据，但用户仍需自行完成信息筛选、事件关联、市场对比和风险归纳。第三方资讯又存在重复转载、标题化表达、发布时间与行情时点不一致等问题，导致用户“看到变化但难以解释变化”。

大模型能够降低信息理解门槛，但通用大模型缺少可靠的实时行情上下文，容易出现时间错配、引用缺失和过度推断。产品机会不是让模型代替用户决策，而是让模型在受控数据边界内完成事实整理、证据关联和风险提示。

## 1.2 现有项目基础

项目说明 PDF 将“今日指数”定义为基于股票实时交易数据的分析与展示产品，已有规划包括国内外大盘指数、行业板块、涨跌榜、涨跌停数量、成交量趋势、个股分时与日/周/月 K 线、主营业务、Excel 导出、用户、角色和权限管理。

SQL 初始化文件包含 11 张表，插入数据不纳入本 PRD 的分析依据。

| 数据域 | 现有表 | 当前可支撑能力 |
| --- | --- | --- |
| 国内指数 | `stock_market_index_info` | 指数开盘、当前、最高、最低、前收、成交量额及时间序列 |
| 国外指数 | `stock_outer_market_index_info` | 指数当前点位、涨跌值、涨幅及时间序列 |
| 行业板块 | `stock_block_rt_info` | 板块公司数、均价、涨跌幅、成交量额及时间序列 |
| 个股行情 | `stock_rt_info` | 个股开盘、当前、最高、最低、前收、成交量额及时间序列 |
| 个股资料 | `stock_business` | 股票名称、所属行业板块和主营业务 |
| 用户权限 | `sys_user`、`sys_role`、`sys_permission`、`sys_user_role`、`sys_role_permission` | 用户、角色、菜单/按钮权限和关联关系 |
| 审计日志 | `sys_log` | 操作人、方法、参数、IP、耗时和操作时间 |

## 1.3 当前能力缺口

1. 缺少自选股、自选分组和个性化跟踪模型。
2. 缺少新闻、公告、来源、去重结果及其与股票/板块的关联模型。
3. 缺少 AI 会话、消息、分析报告、证据引用、反馈和用量记录。
4. 个股表为时间快照结构，未独立定义分时、日、周、月 K 线聚合结果和复权数据。
5. 缺少证券交易所、证券状态、板块类型、交易日历、涨跌停规则等基础元数据，不能在真实产品中统一按 ±10% 判断涨跌停。
6. 表关系按业务逻辑维护，没有数据库外键；符合现有扩展策略，但需要应用层完整性校验和关联表索引。
7. `stock_business.block_label` 为 `varchar(10)`，`stock_block_rt_info.label` 为 `varchar(20)`，存在标识长度不一致风险。
8. `sys_log.user_id` 为字符串，而 `sys_user.id` 为 `bigint`，存在类型不一致风险。
9. `sys_user.email` 注释声明唯一，但 SQL 未建立唯一索引；关系表也缺少防重复联合索引。

## 1.4 建设机会

平台以现有行情数据为可信底座，引入授权新闻和公告，建立“数据聚合、AI 分析、证据核验、自选跟踪、历史沉淀”的完整闭环。相比单纯 CRUD 行情系统，平台应体现以下互联网产品特征：

- 面向任务而不是面向数据表组织页面。
- 允许游客低门槛体验行情，通过 AI 和个性化能力完成注册转化。
- 对外部数据和模型具备缓存、限流、熔断、降级和状态提示。
- 对 AI 内容实施证据、时效、风险声明和用户反馈机制。
- 通过行为指标验证用户是否真正获得研究效率提升。

## 1.5 产品边界

- MVP 聚焦中国 A 股；国内外指数仅用于市场环境参考。
- 产品不连接券商账户，不接收交易委托，不执行自动交易。
- 产品不管理真实或模拟持仓，不计算组合收益。
- 产品不提供保证性预测、确定性评级、具体仓位或目标收益。
- 资讯和公告仅使用具有使用授权的数据源，不采用无授权网页抓取。

# 2. 项目目标

## 2.1 用户目标

1. 在一个页面内完成“看行情、看原因、查证据”，减少跨平台搜索。
2. 快速理解个股、板块或市场的主要变化，并明确数据所处时间点。
3. 将重点股票加入自选，形成可持续的个人研究入口。
4. 保存、检索、追问和复用历史分析，降低重复研究成本。
5. 在信息不足时获得明确提示，而不是接收未经证实的强结论。

## 2.2 产品目标

1. 建立稳定、可降级的行情与资讯数据底座。
2. 形成市场、板块、个股和多标的对比四类 AI 分析场景。
3. 建立 AI 结果的证据引用、时效标记、风险提示和反馈闭环。
4. 通过游客行情体验与登录后 AI 能力形成自然转化路径。
5. 保留现有 RBAC 与审计基础，满足运营管理和问题追踪需要。

## 2.3 北极星指标

北极星指标为“AI 有效分析次数”。一次分析同时满足以下条件才计为有效：

1. AI 任务状态为“已完成”，不是失败、取消或超时。
2. 结果包含核心结论、行情依据、风险与不确定性、数据截止时间和免责声明。
3. 结果至少包含一项行情证据和一条新闻或公告证据；无资讯证据的结果仅记为“受限分析”，不计入北极星指标。
4. 用户打开完整结果并使结果主体进入可视区；重复刷新同一结果不重复计数。
5. 同一用户对同一分析结果只计一次。

## 2.4 MVP 指标与质量护栏

| 指标 | 定义 | MVP 目标 |
| --- | --- | --- |
| AI 有效分析用户占比 | 周内至少完成 1 次有效分析的用户数 / 周活跃注册用户数 | 上线后第 4 周不低于 40% |
| 人均有效分析次数 | AI 有效分析次数 / 使用 AI 的周活跃用户数 | 每周不低于 3 次 |
| AI 任务成功率 | 正常完成任务数 / 发起任务数，排除用户主动取消 | 不低于 95% |
| 引用覆盖率 | 含完整证据引用的已完成分析数 / 已完成分析数 | 100% |
| 用户有用率 | 点赞或选择“有帮助”的反馈数 / 已提交反馈数 | 不低于 70% |
| 游客注册转化率 | 从公开行情页进入注册并完成注册的用户数 / 触发登录门槛的游客数 | 不低于 10% |
| 7 日留存率 | 注册后第 7 日仍产生有效访问的用户数 / 当日新增用户数 | 不低于 25% |
| 数据时效达标率 | 交易时段内数据延迟不超过目标的数据请求数 / 总数据请求数 | 不低于 99% |

> 指标目标用于 MVP 上线后四周的产品验证，不替代系统验收指标。若样本不足 500 名注册用户，应同时展示绝对人数，避免仅用比例得出结论。

## 2.5 非目标

MVP 不以预测涨跌准确率、推荐收益率、交易转化率作为目标，也不以增加用户交易频率为产品成功标准。

# 3. 目标用户

## 3.1 核心用户画像

| 用户角色 | 典型特征 | 核心场景 | 核心诉求 | 产品权限 |
| --- | --- | --- | --- | --- |
| 行情游客 | 未登录，可能首次访问；具备基础股票概念 | 查看市场、榜单、板块和个股行情 | 快速判断平台数据价值，低成本体验 | 浏览公开行情和资讯摘要；不能使用 AI、自选、历史和导出 |
| 注册投资者 | 关注若干 A 股，能够理解涨跌幅、成交量和 K 线 | 研究个股异动、比较标的、持续跟踪自选 | 减少信息搜集时间，获得有证据的结构化解读 | 使用全部前台 MVP 功能 |
| 进阶投资者 | 有稳定观察列表，关注市场与板块联动 | 多标的对比、复盘、沉淀研究记录 | 提高复盘效率，复用历史观点 | 与注册投资者相同，使用频率更高 |
| 系统管理员 | 平台运营、数据或技术支持人员 | 用户权限、数据源、AI 服务和日志管理 | 保障服务可用、成本可控和问题可追溯 | 访问后台管理能力，不默认查看用户私密会话正文 |

## 3.2 典型用户故事

- 作为游客，我希望无需登录即可查看市场和个股行情，以判断平台是否值得使用。
- 作为注册用户，我希望在个股页面直接生成带引用的 AI 解读，而不必复制股票代码到其他工具。
- 作为注册用户，我希望把关注股票分组保存，并从自选列表快速发起分析。
- 作为注册用户，我希望查看 AI 使用了哪些行情和资讯，以便自行核验。
- 作为注册用户，我希望删除不再需要的会话和报告，以管理个人数据。
- 作为管理员，我希望发现数据采集延迟、AI 调用异常和成本突增，并能定位相关日志。

# 4. 用户核心痛点

| 痛点 | 现状表现 | 产品机会 | 成功表现 |
| --- | --- | --- | --- |
| 信息分散 | 行情、新闻、公告和观点分布在不同平台 | 在个股和板块上下文中聚合关联信息 | 用户无需离开当前研究页面即可完成核验 |
| 异动难解释 | 用户看到涨跌或放量，但不知道可能关联哪些事件 | AI 基于量价、板块和资讯给出结构化线索 | 结论可回溯到具体数据和来源 |
| 资讯噪声大 | 重复转载、标题党、旧闻重提影响判断 | 来源授权、去重、时间排序和标的关联 | 同一事件不重复刷屏，发布时间清晰 |
| 专业门槛高 | 指标多、术语多，用户难以建立完整分析框架 | 固定分析模板同时解释术语和风险 | 用户能理解“发生了什么、依据是什么、还缺什么” |
| AI 不可信 | 通用模型可能引用不存在的信息或忽略数据时效 | 强制证据、截止时间和证据不足提示 | 无引用不输出事实性结论，推测与事实分离 |
| 跟踪成本高 | 用户每天重复搜索同一批股票 | 自选分组、快捷分析和历史沉淀 | 用户从自选列表完成日常研究 |
| 研究难复用 | 临时结论散落，无法搜索和比较 | 保存会话、报告、场景和标的元数据 | 历史分析可以按股票、场景和时间检索 |
| 服务异常不透明 | 数据停更或模型失败时，用户不知道结果是否可信 | 展示数据状态、更新时间和降级原因 | 用户能区分实时、延迟、缓存和不可用状态 |

# 5. 核心业务流程

## 5.1 总体价值流程

1. 用户进入市场总览，查看指数、涨跌分布、成交趋势和热点板块。
2. 用户通过榜单、板块成分股或全局搜索进入个股详情。
3. 用户核对实时行情、分时/K 线、主营业务和关联资讯。
4. 用户选择“解读异动”“总结近期信息”或“与其他标的对比”等 AI 场景。
5. 系统检查登录状态、配额和数据新鲜度，聚合行情与资讯上下文。
6. AI 流式输出结论、证据、风险和数据截止时间。
7. 用户点击证据核验、继续追问、提交反馈、保存结果或加入自选。
8. 用户后续从自选中心或分析历史继续研究，形成持续使用闭环。

## 5.2 游客转化流程

1. 游客可浏览公开行情、榜单、板块、个股和资讯摘要。
2. 游客点击 AI、自选、历史或导出时，系统保留当前页面和目标标的并弹出登录说明。
3. 用户选择登录或注册；完成后返回原页面并恢复原操作上下文。
4. 登录/注册失败时保留原页面，不清空用户已选择的标的和场景。

## 5.3 AI 分析流程

1. 用户选择分析场景、目标和时间范围，可补充不超过 500 字的问题。
2. 系统进行参数、权限、配额、交易标的和内容安全校验。
3. 系统获取最新行情、历史区间、板块、主营业务及关联资讯，并记录各数据的截止时间和来源。
4. 若核心行情缺失，终止任务并提示；若部分资讯缺失，允许生成“受限分析”并显著说明限制。
5. 系统调用第三方 LLM，前端按“准备数据、正在生成、生成完成”展示状态。
6. 系统对结果执行结构、引用、禁用表达和来源一致性校验。
7. 校验通过后保存会话、消息、报告、引用和用量；校验失败则重试一次，仍失败时返回可恢复错误。
8. 用户可追问、取消、重试、查看引用、点赞/点踩或删除历史。

## 5.4 AI 任务状态

`待校验 -> 准备上下文 -> 生成中 -> 结果校验 -> 已完成`

任一执行状态可进入：`已取消`、`失败`、`超时`。失败或超时任务不扣减成功配额；已产生第三方调用成本时仍记录内部用量，但不对用户显示技术计费信息。

## 5.5 自选跟踪流程

1. 登录用户在榜单、板块成分股或个股详情点击“加入自选”。
2. 用户选择默认分组或自定义分组；同一股票在同一分组内不得重复。
3. 自选中心展示最新价格、涨跌幅、数据时间和最新资讯数量。
4. 用户可从单个标的发起 AI 分析，也可选择 2 至 3 个标的进行对比。
5. MVP 不提供价格和资讯通知，自选变化仅在用户主动访问时展示。

## 5.6 后台运营流程

1. 管理员登录后按 RBAC 获取菜单和按钮权限。
2. 管理员查看行情、资讯采集任务和 AI Provider 的健康状态。
3. 发生异常时，根据任务、数据源、错误码、时间和追踪标识定位日志。
4. 管理员可管理用户状态、角色和权限，但不可直接查看用户密码、Token、完整请求密钥或未授权的私密会话正文。
5. 所有管理变更写入审计日志，并记录操作前后摘要。

# 6. 完整功能模块

## 6.1 功能地图

| 模块 | 核心能力 | 当前基础 | MVP 建设属性 | 主要依赖 |
| --- | --- | --- | --- | --- |

## 6.2 跨模块业务规则

1. 所有行情卡片和图表必须展示数据截止时间；交易时段数据超过 60 秒未更新时标记“延迟”。
2. A 股涨跌停按证券所属板块、上市状态、特殊处理状态和当日规则计算，不在前端硬编码 ±10%。
3. 上涨使用红色、下跌使用绿色、平盘使用中性色；同时显示正负号，不能只依赖颜色表达。
4. 股票代码在系统内使用六位代码加交易所标识作为唯一业务标识，避免沪深同码或未来市场扩展冲突。
5. 金额、成交量、价格和比例统一由后端返回原始数值与展示单位，前端不得二次推断口径。
6. 游客触发受限功能时统一进入登录引导，并携带返回地址和待执行动作。
7. 用户数据按用户 ID 隔离；管理员只有统计与审计权限时不得查看用户私密内容。
8. AI 输出中的事实、推断和风险必须在视觉上可区分；引用失效不能静默隐藏。

## 6.3 产品技术边界与数据流

1. Vue3 PC Web 通过 HTTPS 访问 Spring Boot 业务接口，前端不直接连接 MySQL、Redis、行情源、资讯源或 LLM Provider。
2. 行情和资讯采集任务从授权第三方数据源获取数据，完成标准化、幂等、去重和质量校验后写入 MySQL，并刷新 Redis 热点缓存。
3. Spring Boot 负责身份权限、行情查询、自选、历史、配额、上下文聚合和 AI Provider 编排；MySQL 保存最终业务记录，Redis 保存可重建状态。
4. AI Provider 只接收去标识化的结构化行情、资讯证据和必要会话上下文，输出经结构、引用和安全校验后才写入报告并返回用户。
5. MVP 由 Spring Boot 直接编排第三方 LLM API；V1.2 若达到独立扩缩容或多模型编排条件，再把 AI 编排迁移到 Python + FastAPI，前端协议与业务对象保持兼容。

### 7.7.3 AI 结果展示模板

1. 分析对象与数据范围。
2. 核心结论，限制为 3-5 条短句。
3. 行情与量价依据，区分最新快照和区间统计。
4. 市场/板块/多标的对比。
5. 资讯与事件线索，按发布时间排列。
6. 风险、反例和不确定性。
7. 信息缺口与建议核验项。
8. 数据截止时间与来源清单。
9. “内容仅用于信息与研究辅助，不构成投资建议”的固定声明。

# 8. 页面结构

## 8.1 全局框架

PC Web 最小验收视口为 1280 × 720，推荐设计基准为 1440 × 900。页面由以下区域组成：

1. 顶部栏：品牌入口、全局股票搜索、市场状态、数据时间、用户入口。
2. 左侧导航：市场总览、行情榜单、板块分析、资讯中心、AI 研究、自选中心、分析历史；管理员额外显示系统管理。
3. 主内容区：页面标题、关键指标、筛选区、数据卡片、图表和列表。
4. AI 侧栏：在市场、板块和个股页面按需展开，默认宽度 420 像素，可调整到页面宽度的 30%-50%。
5. 全局反馈层：登录弹窗、确认弹窗、操作提示、任务状态、异常提示和帮助说明。

左侧导航可折叠，但不能遮挡主要操作。浏览器刷新后保留当前路由、筛选条件和已完成的 AI 结果；生成中的 AI 任务根据任务 ID 恢复状态。

## 8.3 关键页面结构

### 8.3.1 市场总览

从上至下依次为市场状态与数据时间、国内外指数卡、涨跌分布、涨跌停统计、成交趋势、热点板块和市场 AI 解读入口。任何局部组件失败不得导致整页空白。

### 8.3.2 个股详情

首屏左侧展示股票身份与实时行情，右侧提供加入自选和 AI 操作；第二屏为分时/K 线主图与成交量副图；下方依次为主营业务与板块、关联资讯、数据口径。AI 侧栏打开后压缩主内容宽度，不覆盖关键价格和分析上下文。

### 8.3.3 AI 研究工作台

左栏为会话列表，中栏为场景配置与消息流，右栏为上下文和证据面板。对比场景在中栏顶部固定显示 2-3 个标的，防止用户忘记当前比较对象。来源详情在右栏打开，不中断消息流。

### 8.3.4 系统管理

后台与前台使用同一账户体系但独立导航。运行状态首页优先展示红色异常、黄色延迟和绿色正常；颜色同时配合文字和图标。密钥、密码、Token 和验证码永不在页面明文回显。

## 8.4 通用交互规则

1. 页面首次加载使用骨架屏；超过 3 秒仍未完成时显示阶段说明，不使用无限旋转图标。
2. 空状态说明“为什么为空”和“下一步能做什么”。
3. 危险操作必须二次确认，确认内容包含具体对象和影响。
4. 表格筛选、排序、分页写入 URL 查询参数；返回页面时恢复状态。
5. 所有外部资讯链接在新窗口打开，并显示来源域名或来源名称。
6. 图表必须支持鼠标悬浮读取精确数据；涨跌不能只用颜色区分。
7. AI 流式输出期间允许浏览其他页面；任务完成后使用站内提示，不发送 MVP 范围外通知。

# 9. 用户操作流程

## 9.1 游客查看个股并转化为注册用户

1. 游客进入市场总览，从涨幅榜或全局搜索选择股票。
2. 系统打开个股详情，展示最新行情、K 线、主营业务和资讯摘要。
3. 游客点击“AI 解读”或“加入自选”。
4. 系统记录当前股票、场景、时间范围和返回地址，展示登录引导。
5. 游客选择注册，完成邮箱验证和账户创建。
6. 系统自动建立登录态并返回原个股页，恢复待执行动作。
7. 若待执行动作为 AI 分析，系统再次展示上下文摘要，由用户确认后调用 AI；不得在注册完成后自动消耗配额。

## 9.2 登录用户完成个股异动研究

1. 用户进入个股详情并选择“异动解读”。
2. 系统默认选择最近 5 个交易日，展示将使用的行情、板块、主营业务和资讯截止时间。
3. 用户可调整到 1 或 20 个交易日，或输入补充问题。
4. 系统校验数据和配额，创建任务并显示准备进度。
5. AI 流式输出；用户可停止生成，但停止后已生成内容只作为草稿，不计有效分析。
6. 完成后用户逐条查看行情证据和资讯原文。
7. 用户可追问“这次变化与所属板块相比是否异常”等上下文问题。
8. 用户提交有用/无用反馈，结果自动保存在历史中。

## 9.3 从自选股发起多标的对比

1. 用户进入自选中心并切换到目标分组。
2. 用户勾选 2-3 只股票，点击“AI 对比”。
3. 系统固定统一时间范围和数据截止时点，展示每只股票的数据完整度。
4. 若某只股票数据严重缺失，用户选择移除该股票或继续受限分析。
5. AI 输出统一维度对比、共同点、差异、板块背景和风险，不给出“最佳买入”排序。
6. 用户可从结果进入任一个股详情，返回时保留对比会话。

## 9.4 查看旧分析并使用最新数据重做

1. 用户在分析历史中按股票和日期检索会话。
2. 系统展示原结果，并保留原始数据截止时间和引用状态。
3. 用户点击“使用最新数据再次分析”。
4. 系统复制场景、标的、时间范围和用户问题，但重新获取行情与资讯。
5. 新任务形成独立结果，并与原结果互相引用；原结果不被覆盖。

## 9.5 管理员处理行情延迟

1. 监控发现交易时段行情延迟超过 60 秒，市场页面自动显示延迟状态。
2. 系统向有权限管理员发出后台告警，并记录受影响数据源和任务。
3. 管理员进入采集监控，查看最后成功时间、错误摘要和追踪标识。
4. 管理员确认不存在正在执行的同类任务后手动重跑。
5. 重跑成功后数据状态恢复，审计日志记录操作人和结果；失败则维持降级并升级告警。

## 9.6 登录态失效恢复

1. 用户在填写 AI 问题或管理自选时登录态失效。
2. 系统暂停受限请求，保留未提交文本、标的、筛选和当前路由。
3. 用户完成重新登录后返回原位置。
4. 系统重新校验权限、配额和数据时效，用户再次确认后执行写操作。
5. 登录失败或用户取消时，不丢失本地页面上下文，但不执行受限请求。

## 10.2 MVP 明确不包含

- 移动 App、小程序和移动 Web 专项适配。
- 实盘交易、券商账户连接、自动下单和条件单。
- 模拟组合、真实持仓、收益归因和资产管理。
- 确定性价格预测、买卖评级、具体仓位和收益承诺。
- 策略回测、因子平台和量化交易引擎。
- 社区、关注用户、评论、直播和内容创作者体系。
- 付费订阅、订单、发票和商业化套餐。
- 机构多租户、团队协作和审批工作流。
- AI 报告 PDF/Markdown 导出，延后至 V1.1。
- Python + FastAPI 独立 AI 服务，延后至 V1.2。

## 10.3 MVP 发布完成定义

1. 本文所有 `P0` 需求通过功能验收，`P1` 未完成项有明确灰度或后续排期。
2. 游客、注册用户和管理员三类端到端主流程通过测试。
3. 行情与资讯达到时效要求，异常时能正确降级且不展示伪实时数据。
4. AI 正常、受限、失败、超时、取消、限流和引用失效场景均通过验收。
5. 安全测试未发现高危越权、密码/Token 明文、SQL 注入或日志敏感信息泄露。
6. 性能和并发基线达标，核心监控、告警和审计可用。
7. 产品、设计、研发、测试和运维共同完成上线评审。

| 主要页面首屏 | P75 不超过 2 秒，P95 不超过 3 秒 | 20 Mbps 网络、缓存命中、主流 4 核 PC，不含第三方原文页面 |
| 行情查询接口 | 缓存命中时 P95 不超过 1 秒，P99 不超过 2 秒 | 服务端从收到请求到返回完整响应 |
| 搜索建议 | P95 不超过 500 毫秒 | 输入防抖完成后至结果返回 |
| 普通写操作 | P95 不超过 2 秒 | 自选、反馈、标题和个人资料更新 |
| AI 首段内容 | P95 不超过 5 秒 | 用户确认提交至收到首个有效文本片段 |
| AI 完整结果 | P95 不超过 30 秒 | 不含用户主动取消；60 秒强制进入超时状态 |
| 浏览并发 | 支持 500 个并发浏览会话 | 持续 30 分钟，错误率不超过 1% |
| AI 并发 | 支持 30 个并发生成任务 | 不含 Provider 自身限额导致的可识别限流 |
| Excel 导出 | 5,000 行内 P95 不超过 30 秒 | 从提交导出到文件可下载 |

## 11.2 数据时效与一致性

1. A 股交易时段的个股和国内指数数据目标延迟不超过 60 秒；板块聚合目标延迟不超过 60 秒。
2. 资讯和公告从授权源可用到平台可见的目标延迟不超过 5 分钟。
3. 页面、导出文件和 AI 结果分别展示自己的数据截止时间，不以页面加载时间替代数据时间。
4. 榜单、市场广度、板块排行和同一次 AI 对比使用一致的快照基准；允许的快照时间差不超过 60 秒。
5. 交易日、证券状态和涨跌停规则采用版本化元数据；历史计算使用对应交易日生效的规则。
6. 数据采集使用幂等业务键，重复数据不得改变既有正确记录。
7. MySQL 为业务记录最终来源；Redis 只保存可重建的缓存、会话、限流和任务状态。

## 11.3 可用性与降级

1. MVP 月度可用性目标为 99.5%，不包含提前公告的计划维护和已明确标记的第三方原文不可用。
2. 行情源异常时优先展示最近成功快照，并标明“缓存数据”和真实截止时间。
3. 资讯源异常不阻塞基础行情；AI 可在行情完整时生成“受限分析”，但不得计为有效分析。
4. LLM Provider 异常不阻塞行情、自选和历史查看；AI 入口展示当前不可用原因和稍后重试建议。
5. Redis 不可用时，公开行情可退回数据库读取并启用保护性限流；登录、配额或任务状态无法安全保证时暂停相关写操作。
6. 单个组件失败不得造成整页白屏；错误边界按指数、图表、榜单、资讯和 AI 组件隔离。

## 11.4 安全要求

1. 全站生产环境使用 HTTPS；Cookie 使用 `HttpOnly`、`Secure` 和适当的 `SameSite` 策略。
2. 密码使用 BCrypt 等抗暴力破解算法加密，不允许可逆加密或明文存储。
3. 访问令牌、刷新凭据、验证码、LLM 密钥和数据源密钥不得写入前端存储、业务日志或导出文件。
4. 前后端分别执行身份和权限校验；对象级权限必须校验资源所属用户，防止水平越权。
5. 登录、验证码、AI 生成、搜索和导出均设置用户/IP 组合限流与异常频率告警。
6. 所有输入执行长度、类型、枚举和内容校验；防护 SQL 注入、XSS、CSRF、文件公式注入和外链跳转风险。
7. Excel 中以 `=`、`+`、`-`、`@` 开头的用户可控文本进行安全转义，避免公式注入。
8. 第三方资讯送入模型前移除脚本、隐藏指令和提示注入内容；资讯正文不能改变系统级 AI 规则。
9. 管理员高风险操作需要二次确认；超级管理员权限变更记录独立安全日志。

## 11.5 隐私与数据留存

| 数据 | 留存策略 | 用户控制 |
| --- | --- | --- |
| 账户资料 | 账户存续期间保留；注销能力在 V1.1 完善 | 用户可修改，敏感字段脱敏展示 |
| 自选股 | 用户删除或账户清理前保留 | 用户可随时增删和调整分组 |
| AI 会话与报告 | 默认保留；用户删除后隐藏并进入 30 天清理期 | 用户可查看、改名、收藏和删除 |
| AI 反馈 | 与结果关联保留；结果清理后匿名化统计字段 | 用户可更新自己的反馈 |
| 行情原始快照 | 热数据至少 90 天；聚合 K 线至少 5 年 | 公共数据，无个人删除入口 |
| 资讯元数据 | 最长 3 年，受数据源授权期限约束 | 公共数据，无个人删除入口 |
| 操作与安全日志 | 在线保留 180 天，之后按安全策略归档或清理 | 普通用户不可访问后台日志 |

调用第三方 LLM 时只发送完成分析所需的行情、资讯、场景和去标识化会话上下文，不发送用户名、邮箱、手机号、IP、角色、密码、Token 或其他无关个人信息。

## 11.6 AI 质量要求

1. 已完成结果的固定章节完整率为 100%。
2. 所有可外部核验的事实必须绑定行情或资讯证据；无证据时使用“信息不足”表达。
3. 引用必须能定位到具体指标时点或资讯记录，不能只写笼统的“据公开资料”。
4. 同一对比任务中的价格区间、收益口径和数据截止时点保持一致。
5. 模型不得把相关性表述为因果关系；“可能关联”与“已由公告确认”必须明确区分。
6. 结果必须包含至少一项风险或反例；没有发现时说明检索范围和信息限制。
7. 上线前建立覆盖市场、板块、个股、对比、无资讯、旧闻、提示注入和交易建议诱导的评测集。
8. 每次修改模型、提示词、上下文结构或引用校验规则，都需要通过回归评测后灰度发布。

## 11.7 兼容性与易用性

1. 支持当前及前一个主要版本的 Chrome 和 Edge。
2. MVP 仅验收 1280 × 720 及以上 PC 视口，不承诺移动端体验。
3. 核心功能可通过键盘完成搜索、列表选择、表单提交和弹窗关闭。
4. 文本与背景对比度满足基本可读性；涨跌使用颜色、符号和文字三重表达。
5. 数值统一使用千分位；价格保留证券规定精度；百分比显示正负号；大额数值支持元、万、亿切换但保留原始值提示。
6. 所有时间明确到日期、时分秒和时区；相对时间旁可查看绝对时间。

## 11.8 可观测性与审计

1. 所有前后端请求携带统一追踪 ID，AI 任务、行情聚合和资讯采集可关联查询。
2. 监控请求量、错误率、P95/P99 延迟、缓存命中率、数据库连接、任务积压和数据延迟。
3. AI 监控 Provider、模型、场景、首段延迟、完整延迟、成功率、Token 用量、结构校验失败和安全拦截。
4. 告警至少覆盖行情延迟、资讯延迟、AI 熔断、错误率突增、配额异常、数据库容量和审计日志不可用。
5. 日志采用字段白名单和脱敏策略；生产环境禁止记录完整请求正文和完整模型上下文。

# 12. 异常场景

| 编号 | 异常场景 | 用户侧表现 | 系统处理 | 记录与恢复 |
| --- | --- | --- | --- | --- |
| EX-01 | 行情源短时不可用 | 页面显示缓存标记、截止时间和刷新入口 | 返回最近成功快照，不阻塞资讯和历史 | 记录数据源错误；恢复后自动刷新状态 |
| EX-02 | 交易时段行情超过 60 秒未更新 | 显示“行情延迟”，不显示“实时” | 停止基于伪实时数据计算新榜单；允许查看旧值 | 触发告警；新数据到达后重新计算 |
| EX-03 | 无任何行情缓存 | 对应组件显示暂不可用 | 不返回 0 或空价格；AI 核心分析禁止发起 | 记录受影响标的和源；支持手动重试 |
| EX-04 | 单只股票停牌 | 展示停牌和最近有效价格 | 不计入正常涨跌排行；允许查看资料和历史 | 记录证券状态版本 |
| EX-05 | 非交易日或收盘后 | 展示最近交易日与市场状态 | 不提示数据延迟；使用最近收盘数据 | 无需告警，除非与交易日历冲突 |
| EX-06 | 涨跌停规则元数据缺失 | 涨跌停统计显示不可计算 | 不默认按 10% 判断；其他涨跌统计继续 | 记录元数据缺口并告警 |
| EX-07 | 板块与股票映射不一致 | 板块详情标记成分数据不完整 | 不用模糊名称强行补齐；相关 AI 标记受限 | 进入数据质量列表，修复后重算 |
| EX-08 | 资讯源延迟或部分失败 | 展示资讯截止时间和部分来源不可用 | 保留可用来源；去掉“最新”标签 | 按来源记录失败率并告警 |
| EX-09 | 资讯重复或旧闻重发 | 用户只看到一条主事件记录 | 合并重复记录并保留来源列表；原发布时间优先 | 保存内容指纹和合并轨迹 |
| EX-10 | 资讯关联置信度低 | 不进入个股默认资讯和 AI 证据 | 标记待确认，管理员可纠正 | 保存候选和关联原因 |
| EX-11 | 资讯原文链接失效 | 显示“来源暂不可访问” | 保留标题、来源、发布时间和授权摘要 | 定时复查链接；不删除历史引用 |
| EX-12 | LLM Provider 超时 | 生成状态转为超时，显示重试 | 60 秒中止等待；不扣用户成功配额 | 记录 Provider、模型、耗时和追踪 ID |
| EX-13 | LLM 返回格式不完整 | 用户暂不看到错误结果 | 自动校验并重试 1 次；仍失败则返回可恢复错误 | 保存校验原因，不保存为完成报告 |
| EX-14 | AI 引用不存在或与正文冲突 | 显示生成失败而非无引用结论 | 阻止发布结果；执行一次修复重试 | 记录引用校验失败类型 |
| EX-15 | 资讯含提示注入文本 | 用户不感知恶意指令 | 清洗隔离，资讯只能作为数据，不能覆盖系统规则 | 记录安全命中，不记录不必要的恶意全文 |
| EX-16 | 用户诱导 AI 给出买卖、仓位或保证收益 | 返回产品边界说明和研究辅助替代选项 | 不生成可执行交易指令 | 记录安全分类，不记录敏感个人内容 |
| EX-17 | AI 配额耗尽 | 显示剩余 0 次和下次重置时间 | 不创建任务、不调用 Provider | 配额按自然日自动恢复 |
| EX-18 | 用户并发发起超过 2 个 AI 任务 | 新任务被拒绝，已有任务不受影响 | 返回并发限制和任务入口 | 任务完成/取消后立即释放并发额度 |
| EX-19 | 用户在生成中关闭页面 | 再次打开可恢复任务状态 | 后台继续任务，除非用户明确取消 | 按任务 ID 恢复；完成后写入历史 |
| EX-20 | 登录态在操作中失效 | 弹出登录提示并保留输入 | 暂停请求；重新登录后重新校验 | 恢复原路由和待执行动作 |
| EX-21 | 账号锁定或停用 | 明确提示不可登录或会话失效 | 立即撤销会话和权限缓存 | 写入安全日志；仅授权管理员可恢复 |
| EX-22 | 自选重复添加或达到上限 | 重复添加提示已存在；超限提示整理分组 | 重复请求幂等；达到上限不写入 | 记录正常业务结果，不报系统异常 |
| EX-23 | 历史结果引用已失效 | 原结果仍可读，引用标记失效 | 不重写旧结果；提供使用最新数据再次分析 | 保留原引用元数据和状态变化 |
| EX-24 | Excel 数据超限或生成失败 | 提示缩小范围或重试 | 超过 5,000 行不生成；失败文件不提供下载 | 记录导出条件、失败原因和用户 |
| EX-25 | Redis 不可用 | 公开行情可能变慢；登录/AI 显示服务受限 | 公开读请求受保护地回源；依赖会话或幂等的写操作暂停 | 高优先级告警；恢复后重建可重建缓存 |
| EX-26 | 数据库不可用 | 页面展示缓存数据和系统维护提示 | 停止所有写操作；禁止将缓存当作持久化成功 | 最高级别告警；恢复后执行一致性检查 |
| EX-27 | 审计日志写入失败 | 普通前台读取不受影响 | 管理高风险写操作暂停，普通操作按策略降级 | 触发高优先级告警，恢复后核对缺口 |
| EX-28 | 管理员并发修改同一权限 | 后提交者收到数据已更新提示 | 使用版本校验拒绝覆盖 | 展示最新版本，用户确认后重新提交 |

| 对比标的 | 对比场景必填 | 总标的数 2-3 个 |
| 用户问题 | 否 | 最多 500 字，不得改变系统安全规则 |
| 会话标识 | 追问时必填 | 指向当前用户拥有的有效会话 |
| 客户端请求标识 | 是 | 用于防重复提交和结果关联 |

## A.3 AI 分析结果

| 字段 | 说明 |
| --- | --- |
| 任务与报告标识 | 支持状态查询、历史查看、重试和追踪 |
| 状态 | 准备中、生成中、校验中、完成、受限、失败、超时或取消 |
| 固定章节 | 核心结论、行情依据、对比、事件、风险、信息缺口和声明 |
| 数据截止时间 | 行情和资讯分别记录，不合并成模糊时间 |
| 证据列表 | 编号、类型、来源、数值/摘要、时间、链接和有效状态 |
| 受限原因 | 资讯缺失、数据陈旧、关联不确定或其他可解释限制 |
| 模型元数据 | Provider、模型和模板版本，仅后台可见完整信息 |
| 用量摘要 | 内部 Token 和成本；前台只展示剩余用户配额 |

## A.4 统一状态语义

- `正常`：数据在目标时效内且核心字段完整。
- `延迟`：有可用数据，但超过目标时效。
- `缓存`：来自最近成功快照，不代表当前实时状态。
- `受限`：核心结果可生成，但部分证据或数据源缺失。
- `不可用`：缺少完成该功能所需的核心数据或服务。

## A.5 服务交互约定

1. 普通业务接口使用 HTTPS + JSON，统一返回业务状态、用户可理解的消息、业务数据、追踪 ID 和服务端时间。
2. 列表接口统一返回数据项、总数、页码和每页数量；筛选、排序和分页参数的默认值由服务端定义并在接口文档中保持一致。
3. HTTP 状态表达传输、认证、权限和服务状态，业务状态表达具体失败原因；前端不能仅根据消息文本判断结果。
4. 大于 JavaScript 安全整数范围的 ID 以字符串返回，避免用户、会话、任务和报告 ID 精度丢失。
5. AI 首次提交返回任务 ID；生成内容使用 SSE 单向流传输任务状态、文本片段和完成事件，断线后可按任务 ID 查询最终状态。
6. AI 取消使用独立的幂等操作；同一任务重复取消返回相同最终状态，不创建新任务。
7. SSE 不可用时，前端降级为按任务 ID 轮询状态；轮询只作为兼容方案，不改变 60 秒超时和配额规则。

# 附录 B：行情计算口径

| 指标 | 口径 |
| --- | --- |
| 涨跌值 | 当前有效价格 - 前收价格 |
| 涨跌幅 | （当前有效价格 - 前收价格）/ 前收价格 × 100%；前收缺失或为 0 时不计算 |
| 振幅 | （当日最高价格 - 当日最低价格）/ 前收价格 × 100%；前收缺失或为 0 时不计算 |
| 日 K | 开盘为当日首个有效成交价格，收盘为最后有效成交价格，最高/最低取当日有效价格极值，成交量额按有效记录聚合 |
| 周/月 K | 按交易日历对日 K 聚合；开盘取周期首个交易日，收盘取周期最后交易日，最高/最低取周期极值，成交量额求和 |
| 涨跌停 | 使用证券所属市场、板块、特殊处理状态、上市日期和当日生效规则判断，不使用统一固定比例 |
| 板块领涨股 | 板块有效成分股中，在同一截止时点涨幅最高的股票 |
| 市场上涨/下跌/平盘 | 使用每只可交易股票的最新有效快照互斥分类；停牌和无有效价格单列 |

MVP K 线默认不复权，并在图表上明确显示“不复权”。前复权、后复权及企业行动数据纳入 V1.2。

# 附录 C：需求追踪与评审清单

## C.1 需求追踪

| 用户核心问题 | 对应能力 | 主要验收指标 |
| --- | --- | --- |
| 看到了涨跌但不知道发生了什么 | 市场/板块/个股 AI 解读 | 固定章节完整、引用覆盖 100%、截止时间可见 |
| 资讯太多且重复 | 资讯采集、去重和标的关联 | 重复事件合并、来源可追溯、低置信不进入 AI |
| 不信任 AI 结论 | 证据、风险、受限说明和反馈 | 无虚构引用、事实与推断区分、负向反馈可归因 |
| 每天重复搜索关注股票 | 自选分组和快捷分析 | 自选状态一致、3 个主要操作内完成分析 |
| 历史研究无法复用 | 会话历史、检索和再次分析 | 原结果不被覆盖，新旧结果可追溯 |
| 服务异常时无法判断数据是否可信 | 数据状态、截止时间和降级 | 延迟/缓存/不可用状态明确，不展示伪实时数据 |

## C.2 上线前评审问题

1. 游客、注册用户和管理员是否都能完成各自的主流程？
2. 每项 AI 事实是否都能定位到有效行情时点或资讯来源？
3. 数据延迟、来源失败和模型失败时，用户是否仍能判断当前内容的可信程度？
4. 是否有任何页面把模型推断写成已确认事实，或把研究辅助写成投资建议？
5. 榜单、图表、AI 和导出是否使用一致的数值、单位、时间与涨跌停口径？
6. 用户是否只能访问自己的自选、会话、报告和反馈？
7. 管理员是否能定位采集和 AI 故障，同时无法看到不必要的敏感数据？
8. 所有 P0 需求是否都有正常、空数据、失败、延迟、无权限和重复操作用例？
